## Purpose

让用户依据已经落盘的 OpenSpec 内容，在桌面工作台中完成单个变更的归档检查、规范同步结果审阅和确认执行。所有写入均对应用户看到的具体结果，并在外部文件变更、执行失败或 CLI 能力不足时给出明确且可恢复的状态。

## ADDED Requirements

### Requirement: 归档独立于 Agent 和会话
系统 SHALL 仅依据当前项目的持久化 OpenSpec 内容、兼容 CLI 的规则结果和用户的明确选择执行归档，MUST NOT 要求 Agent 会话、聊天历史、模型凭证或模型服务。系统 MUST NOT 将任务完成或文档结构校验描述为实现验收。

#### Scenario: 没有 Agent 环境仍可归档
- **WHEN** 用户拥有兼容的本地 CLI 和有效 OpenSpec 文件，但未安装或登录任何 AI Agent
- **THEN** 用户仍可完成归档检查、预览、确认及执行

#### Scenario: 内容缺少明确的合并依据
- **WHEN** 增量规范不能按受支持规则产生通过校验的明确结果
- **THEN** 系统展示具体问题并保留原项目文件，允许用户通过自行选择的外部工具修正后重新检查

### Requirement: 归档前展示基于当前文件的检查结果
系统 SHALL 在用户确认之前展示选中 Change、项目、任务完成量、产物的完成或显式跳过状态、归档相关校验结果和目标目录。检查和预览 MUST NOT 修改原项目文件；缺失产物和未完成任务 SHALL 被明确列为待确认警告，通过 CLI 校验失败的内容 MUST 阻止提交。

#### Scenario: 任务全部完成
- **WHEN** 用户对任务全部完成的活跃 Change 发起归档检查
- **THEN** 系统继续检查产物和规范，并说明任务完成状态不代表已经完成实现验收

#### Scenario: 存在未完成任务或产物
- **WHEN** 任务存在未完成项，或者工作流声明的产物既未完成也未显式跳过
- **THEN** 系统列出相应任务数量或产物名称，且在用户明确接受这些警告前不允许提交

#### Scenario: 校验失败或用户取消预览
- **WHEN** 归档相关校验失败，或用户在确认写入前取消操作
- **THEN** 原项目的 Change、正式规范及归档记录保持不变

### Requirement: 展示完整且明确的规范同步结果
系统 SHALL 在确认之前展示每个将新增、修改或删除的正式规范文件及其完整可审阅差异，并区分没有增量规范、已经同步和需要同步三种状态。系统 MUST NOT 使用命令日志替代文件差异，MUST NOT 隐藏将被移除的场景、规范文件或 Purpose。

#### Scenario: 无需修改正式规范
- **WHEN** Change 没有增量规范，或其增量已经体现在正式规范中
- **THEN** 系统显示具体原因、说明正式规范不会改变，并允许用户审阅目录归档后确认执行

#### Scenario: 需要更新正式规范
- **WHEN** CLI 规则产生了有效的正式规范更新结果
- **THEN** 系统展示全部新增、修改和删除文件的差异，以及将保留原有内容的 Change 目录移动

#### Scenario: 规范能力被整体移除
- **WHEN** 有效归档结果将删除某项能力的正式规范文件
- **THEN** 预览明确标识整个文件及其 Purpose 的删除，且只有 CLI 已验证该删除合法时才允许提交

### Requirement: 确认仅授权已审阅的归档结果
系统 SHALL 要求用户在预览完成后明确确认，且一次确认 MUST 仅授权显示的项目、Change、文件结果和归档位置。系统 MUST NOT 在执行阶段隐式增加写入范围，MUST NOT 提供忽略校验或跳过尚未同步规范的快捷选项。

#### Scenario: 确认含有警告的计划
- **WHEN** 用户已明确接受预览中列出的任务或产物警告并确认归档
- **THEN** 系统提交该预览对应的规范结果及目录移动，成功反馈继续保留这些警告

#### Scenario: 重复点击确认
- **WHEN** 同一个归档确认被重复提交
- **THEN** 系统最多执行一次写入，并返回该操作的进行中或既有结果，不产生第二次归档

#### Scenario: 日期命名和目标碰撞
- **WHEN** 系统生成或提交归档计划
- **THEN** 不含日期前缀的 Change 使用当前本地日期命名，已有日期前缀的名称不重复添加日期，且已有目标不得被覆盖

### Requirement: 外部变更使未执行的预览失效
系统 MUST 在提交之前重新检查预览依赖的文件内容、路径、CLI 和归档目标。项目切换、相关文件的增加删除或内容变化、路径替换、CLI 变化或影响归档名称的日期变化 MUST 使旧预览失效，并要求重新检查和审阅；MUST NOT 静默重算结果后沿用旧确认。

#### Scenario: 外部工具改动规范或 Change
- **WHEN** 预览生成后，其他工具修改相关文件，即使保留了原文件大小和修改时间
- **THEN** 提交被拒绝，原计划不写入任何项目文件，界面说明需要重新生成预览

#### Scenario: 预览期间切换项目
- **WHEN** 用户在一个项目中生成预览后切换到另一个项目
- **THEN** 旧预览不能执行，旧请求的结果不能覆盖新项目内容

#### Scenario: 提交时发现目标已存在
- **WHEN** 预览之后另一个操作占用了归档目标
- **THEN** 系统拒绝覆盖目标，并且不先修改正式规范

### Requirement: 归档仅写入允许的项目范围
系统 MUST 将归档写入限制在选中项目的正式规范及选中 Change 的归档移动内，保留 Change 中的元数据和其他原有文件。系统 MUST 拒绝逃逸真实 OpenSpec 根目录、经过受限路径符号链接或触及其他 Change、实现代码和 Initiative 内容的归档结果。

#### Scenario: 预演结果包含额外写入
- **WHEN** 归档计算结果要求修改允许范围之外的文件，或其解析根目录与当前项目不符
- **THEN** 系统拒绝生成可执行计划并说明不受支持的范围，原项目保持不变

#### Scenario: 保留完整 Change
- **WHEN** 用户确认归档包含元数据、规划文档及其他本地文件的 Change
- **THEN** 这些内容被完整保留在已预览的归档目录，不因仅展示 Markdown 而遗漏非 Markdown 文件

### Requirement: 失败和中断必须呈现真实文件状态
系统 SHALL 在写入失败时恢复能够安全恢复的本次变更，并明确区分未写入、已恢复、已完成和需要人工恢复的状态。系统 MUST NOT 为回滚覆盖其他工具的新修改，MUST NOT 在文件状态不确定时报告归档成功；中断后恢复操作 SHALL 保留恢复依据且不得自动覆盖文件。

#### Scenario: 规范写入后目录移动失败
- **WHEN** 部分正式规范已更新，但 Change 移动失败
- **THEN** 系统尝试安全恢复本次规范写入；无法恢复时保留恢复材料，并列出已修改文件、Change 实际位置和处理方式

#### Scenario: 执行期间存在新的外部写入
- **WHEN** 提交或恢复期间检测到其他工具写入了同一路径
- **THEN** 系统停止有冲突的覆盖操作，保留双方内容和恢复依据，并明确要求处理该文件冲突

#### Scenario: 应用在提交期间中断
- **WHEN** 应用再次启动并发现未结束的归档操作
- **THEN** 系统核对实际文件状态，呈现已完成或需要恢复的结果，并在同一项目未决状态解决前阻止新的归档写入

### Requirement: 完成后刷新并定位归档结果
系统 SHALL 在核对文件结果正确之后报告成功，刷新项目内容和提案数量，并允许用户直接查看对应归档记录。系统 SHALL 在预检或执行期间显示状态、防止重复触发，并在尚未写入的阶段允许取消。

#### Scenario: 归档成功
- **WHEN** 规范结果和完整 Change 归档位置均已核对正确
- **THEN** 原活跃 Change 从执行台移除，归档记录可立即打开，结果显示规范同步情况及归档相对路径

#### Scenario: 归档正在提交
- **WHEN** 用户已经确认且归档开始写入
- **THEN** 系统明确显示正在执行，暂时阻止项目切换与重复提交，且不提供会中断多文件提交的取消按钮
