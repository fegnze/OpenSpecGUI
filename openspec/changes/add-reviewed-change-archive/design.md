## Context

动机和首期范围见 `proposal.md`。这是工作台第一次向导入项目写入内容，涉及 CLI、主进程、IPC 和 renderer，需要设计写入边界及失败状态。

- `src/core/openspec-cli.js` 目前仅执行 `list --json`，可以回退到只读文件推断；查询成功不能证明支持归档。
- `src/core/workspace.js` 的 `ready-to-archive` 主要来自任务完成和文档异常状态，尚未检查规范同步或实现验收。
- `WorkbenchService` 已有项目身份、revision、真实根目录检查及内容刷新指纹。但刷新指纹只覆盖部分扩展名，不能直接用于验证整个 Change 的归档内容。
- 当前可用 CLI 的 `archive --json` 是实际写操作，`--yes` 会接受提示；没有只读的归档计划或完整 diff 接口。CLI 内部已有规范增删改及重命名规则，GUI 不复制一套语义合并实现。
- Agent Skill 中的自然语言 guidance 和智能合并是另一种工作流。GUI 仅执行受支持的 CLI 规则，不解释这些自然语言指令，也不宣称两种工作流具有相同的语义判断能力。

## Goals / Non-Goals

**Goals:**

- 用户确认的文件结果与实际提交的结果一致，确认前不改变原项目。
- 由 CLI 计算规范结果，由主进程保存和受限提交计划；renderer 仅展示结果并请求命名操作。
- 不依赖 Git 干净状态或 Agent 环境，在项目切换、外部文件修改和写入失败时保留明确状态。
- 复用现有 Electron 应用和 CLI 解析路径，不启动服务，不引入通用命令执行、任意文件编辑或任务调度框架。

**Non-Goals:**

- 根据代码、测试或聊天内容判断变更是否真正完成。
- 处理需要自然语言解释的规范冲突，或追踪、通知、暂停其他 Agent。
- 管理任意 standalone store、撤销成功归档或扩展其他写操作。CLI 若解析到当前注册项目以外的根目录，本次操作不可用。

## Decisions

### 1. 以隔离文件快照计算预览，提交已经计算的文件结果

优先复用解析到的兼容 CLI，在 GUI 管理的临时项目快照中运行 `archive <change> --json --yes`。这里的 `--yes` 只允许临时快照完成计算，不能构成对原项目的写入授权。

快照包括选中 Change 的所有普通文件及目录、正式规范和 CLI 实际需要的项目配置与工作流定义。复制前后核对源内容，拒绝相关路径中的符号链接及不支持的特殊文件；不复制实现代码、Git 仓库或其他 Change。对于无法在这些输入内重现的自定义工作流，显示不支持该项目的原因。

主进程将命令解析为固定的可执行目标，在临时项目 cwd 下调用，不把项目路径插入 shell。检查 `status`、校验和归档的结构化返回根目录，必须都属于本次快照；原项目解析根目录也必须匹配注册项目。CLI 可执行目标、所需运行时及规则包版本的身份和内容指纹进入计划。预演是对受信兼容 CLI 的文件输入隔离，不宣称为任意可执行文件提供 OS 安全沙箱。

完成后比较快照前后文件树，只接受以下结果：

- 选中 Change 整体移入预期归档位置，原目录不再存在，全部内容和相对路径保留。
- `openspec/specs/**/spec.md` 的新增、修改或合法删除，以及相应空目录的整理。
- 原有项目配置、工作流定义和其他内容不变。

主进程为允许的正式规范变更保存原始字节及最终字节，并校验新结果；差异展示由这些字节生成。无正式规范差异时，结合原始产物区分“无增量规范”和“规范已同步”。无法完整展示的超大结果不生成可执行计划，提示用户通过外部工具处理。

确认后仅提交保存的字节和目录移动，不再调用 live `archive` 重新计算。这样无需复制 CLI 合并算法，也不会在确认后产生未审阅的新结果。

**Alternatives considered:**

- 直接在真实项目调用 `archive --yes`：无法在当前 CLI 接口下先展示完整文件结果。
- 预演后在真实项目重跑 CLI：复用其事务逻辑较方便，但确认与第二次计算之间仍可能产生不同结果。
- GUI 自行实现增量规范合并：增加与不同 CLI 版本产生语义偏差的维护成本。
- 仅移动目录：跳过正式规范同步检查，不满足本次归档闭环。

### 2. 预检与提交使用主进程持有的短期计划

新增窄接口：

- `changes:prepare-archive`：接收 `projectId`、`revision` 和 `changeId`，返回检查结果、差异和不透明 `planId`。
- `changes:commit-archive`：接收相同项目身份、`planId` 以及用户接受的警告标识，不接收路径、命令或文件内容。
- `changes:discard-archive`：取消预览并清理相应临时资源，不影响已进入提交阶段的操作。

写入口核验可信宿主 renderer，并保留现有 payload 限制、字段白名单和项目身份校验。独立 Initiative App 不获得这些接口。

计划保存真实项目根、Change 全量内容指纹、正式规范及配置/工作流输入的内容指纹、CLI 身份、显示日期、目录目标、文件前后内容和检查结果。目标不存在也属于前置条件。计划仅存在主进程，renderer 无权修改，取消、项目切换、相关刷新或应用退出即失效；内存和临时文件有数量、总量及寿命上限。

检查分别展示 CLI 工作流产物状态、任务进度及归档相关文档校验。`done` 与显式 `skipped` 视为产物状态已满足；其他状态和未完成任务形成稳定的警告标识。警告可以由用户明确接受，结构校验错误、非法范围和合并失败不能绕过。计划不把“任务已完成”解释为测试通过或用户验收。

CLI 能力按实际命令契约及兼容性 fixture 判断，不能仅比较版本字符串。当前实现所需的 JSON 输出不受支持时，保留阅读与文件推断，并说明归档不可用。命令超时、输出大小和快照大小各自设限；超时或输出被截断都不能当作可提交结果。

### 3. 确认前重验，写入期间按项目串行

提交时先绑定当前项目和 revision，重查所有计划前置条件，使用内容摘要而非 mtime 或文件大小判断变化。任何差异均返回预览失效，要求重新生成，不能沿用旧确认。

涉及日期前缀的命名使用应用显示的本地日期；已带 `YYYY-MM-DD-` 的 Change 不叠加日期。跨日导致目标名称应变化时旧计划失效。真实归档目标在首次写入前必须仍不存在。

主进程对每个项目一次只允许一个归档提交，重复请求复用同一执行 Promise 或终态结果。开始写入后，UI 与服务层暂时阻止项目选择、移除和重新关联；刷新事件合并到操作结束后处理。预检和预览阶段允许取消，提交阶段不提供强行中止按钮。

GUI 的串行控制不能锁住其他工具，因此每次改变路径前仍需重验相关文件与真实目录，不将执行前的单次检查当作完整并发保护。新增文件使用排他创建，现有文件采用同文件系统的暂存与备份，目标占用或输入变化均中止相应写入。Change 的目录移动以完整内容指纹复核，不能复用仅扫描 Markdown 的读取索引。

### 4. 用窄范围操作记录支撑失败恢复

只为归档操作保存一份恢复记录，位置在 Electron 用户数据目录，按真实项目根与操作 ID 关联。首次写入前持久化目标、原始及期望内容摘要、备份位置和操作阶段；被替换文件的备份与暂存文件放在相应文件所在的文件系统，避免依赖跨卷原子 rename。

提交顺序为：保存恢复依据、重验前置条件、应用规范结果、移动完整 Change、核对最终文件状态、记录成功并刷新。归档目标通过专属占用和“不覆盖已有目录”的检查保护。所有阶段只允许计划内路径；禁止 renderer 或错误信息携带的任意路径触发恢复写入。

失败时逆向恢复本次已完成的步骤，仅在文件仍符合本次操作写入状态且目标可安全恢复时恢复原内容。若其他工具已修改同一路径，保留当前文件和备份，报告精确的未决状态，不能用通用 `git reset` 或整目录覆盖来回滚。此处不承诺跨文件事务原子性或对外部编辑器的排他锁。

应用重启后依据记录与实际文件核对，区分已完成、已恢复和需要人工恢复，不自动覆盖内容。同一项目存在未决恢复状态时继续允许浏览，但阻止新归档写入。成功归档的撤销与规范反向同步不属于这一恢复机制。

工作区加载结果附带当前项目的恢复摘要；界面展示实际路径、备份位置和手动处理说明，用户处理后可重新核对。不为此新增通用文件恢复写入接口。

### 5. 在现有详情页使用可审阅的归档对话框

任务和文档两个详情面板共享同一归档入口。复用现有原生 `<dialog>` 交互形式，不增加携带有效计划的可收藏路由，也不改变 Initiative App 宿主结构。

对话框包含项目和 Change 身份、任务及产物检查、警告接受控件、规范同步状态、逐文件 diff、目录移动目标和最终确认。新增、修改、删除均独立标记，规范退役时明确显示包括 Purpose 在内的整文件删除。差异按文本安全呈现，不作为 Markdown 或 HTML 执行。

有规范变更时确认文案为“同步规范并归档”，无需变更时为“归档”。预检、失效、提交中、失败和成功分别有清晰状态；仅预览阶段的关闭或 Escape 可以取消。长 diff 的滚动和横向阅读不能遮挡身份、警告及确认区域；键盘可访问，关闭后恢复触发按钮焦点。

成功必须先核对真实结果，再刷新并打开对应归档详情。显示规范同步情况、保留的警告和归档相对路径。工作台原有“待归档”保留为任务状态提示，增加归档前仍需检查的解释，避免新增一套推测性的就绪状态。

## Risks / Trade-offs

- [隔离预演依赖 CLI 的真实输入集合] → 首先通过完整兼容性 fixture 验证所选适配契约；无法复现的工作流明确不可用，不悄悄丢弃配置或退回只移动目录。
- [缓存结果提交需要独立的有限文件事务] → 限制为规范文件及单个目录移动，复用现有主进程边界，使用故障注入验证每个写入阶段和恢复路径。
- [任意外部进程可能在任意时刻写入相同文件] → 缩短提交窗口、逐步重验、保留备份，检测冲突后显示真实状态；不声称 GUI 可以控制外部 Agent 的执行。
- [大量规范使快照或 diff 开销过大] → 设置扫描、输出、文件和总体积上限；超过限制时继续浏览并停止本次归档，不能截断预览后允许提交。
- [自然语言项目规则并非 CLI 可执行校验] → 明确归档结果只代表结构及规则处理成功；涉及语义验收和额外项目约定由用户自行确认，不调用 Agent 补判。

## Migration Plan

1. 先建立 CLI 预演与归档计划模块及隔离 fixture，证明原项目在确认前不变，再接入提交和恢复逻辑。
2. 接入命名 IPC 与详情对话框，保留无兼容 CLI 的浏览降级，验证项目切换与独立 App 权限边界。
3. 更新 README 及 `openspec/specs/desktop-workbench/spec.md` 的 Purpose，准确描述浏览与受控管理并存；Purpose 的编辑在实现阶段单独完成，现有能力的 delta 不使用会被 CLI 忽略的 Purpose 覆盖。
4. 完成聚焦测试、完整仓库检查和真实 Electron 交互验证。只用合成项目验证写入，不以真实业务项目归档作为测试手段。
5. 若回退应用版本，既有归档目录和正式规范保持标准 OpenSpec 文件。任何未决恢复记录须先保留并处理，不能通过卸载应用删除恢复依据。
