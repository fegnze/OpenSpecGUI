## Context

现有 renderer 使用原生 HTML、CSS custom properties、Lucide 本地资源和单文件状态渲染，功能面已经由 Electron E2E 覆盖。`styles.css` 已包含明暗颜色、响应式规则和 reduced motion，但表面、状态和排版规则主要随页面逐步形成；首页在最小窗口下会纵向堆叠空泳道，详情页的行动提示、任务列表和上下文栏也存在视觉竞争。

当前 E2E 使用 `node:test` 与 `playwright-core` 驱动 Electron，并将截图写入 `artifacts/`，但截图没有稳定数据、基线比较或差异门禁。安全窗口配置、受限 preload API、renderer CSP 和被导入项目只读边界均为既有约束，本设计不得削弱这些边界。动机见 `proposal.md`，可观察行为见 `specs/workbench-visual-system/spec.md`。

## Goals / Non-Goals

**Goals:**

- 在不迁移前端框架的情况下建立可复用、可审计的视觉 token 与页面层级。
- 让首页、提案详情、文档阅读和项目管理在真实 OpenSpec 数据下形成一致的桌面工具体验。
- 把宽桌面、紧凑桌面和最小窗口作为三种明确布局状态，而不是连续缩小同一布局。
- 让视觉回归、可访问性、键盘路径和文本溢出成为可重复的交付门禁。

**Non-Goals:**

- 不改变 workspace 数据结构、OpenSpec 解析语义、项目注册表、IPC 合约或安全边界。
- 不引入 React、Vue、Tailwind、运行时组件库、远程字体或远程视觉资源。
- 不把动画、插画、营销式空状态或装饰性视觉当作质量提升目标。
- 不在本 change 中引入 GSAP、Storybook、Playwright MCP 服务或云端视觉测试平台。

## Decisions

### 1. 采用“安静的执行工作台”作为统一设计方向

视觉方向以高频扫描、比较和继续执行为核心：中性表面承载结构，语义色只表达状态和焦点，标题和当前任务建立主要层级，机器 ID、时间和来源降为辅助层级。减少英文全大写眉题、重复边框和大面积空容器，但保留对开发者有价值的精确 ID、任务编号和进度。

实现前先基于同一套确定性 fixture 产出“均衡密度”和“高密度”两种可交互探索，覆盖首页、详情和文档页面。Taste Skill 以固定 commit 的项目级审计输入参与比较，但最终方向由本规格和人工截图评审决定，不能直接复制其通用模板。

人工评审已确认采用“均衡密度”作为产品基线，并吸收高密度方向的紧凑提案行元数据对齐。选定 token、三档布局、评审矩阵和代表截图记录在 `docs/design/workbench-visual-baseline.md`，后续实现与视觉回归以该基线为方向约束。

备选方案是直接按 Taste Skill 重写界面；该方案缺少 OpenSpec 领域约束且容易把规则误当产品决策，因此拒绝。另一备选是延续现有页面逐块微调；它无法解决跨页面层级和验收基线问题，也予以拒绝。

### 2. 用语义 CSS token 约束视觉系统

在现有 custom properties 上整理五组 token：

- 排版：界面、正文、数字/机器 ID 三种角色及固定字号层级。
- 空间：4px 基础网格上的页面、区块、控件和行密度。
- 表面：canvas、primary surface、secondary surface、raised overlay 与边界层级。
- 语义：neutral、accent、success、warning、danger、focus，状态组件只消费语义 token。
- 动效：instant、fast、standard 三档时长和少量 easing，并统一 reduced motion 覆盖。

正文优先使用平台系统字体与中文 fallback，monospace 仅用于机器 ID、任务编号和精确数字。组件继续保持小圆角、低阴影和稳定尺寸，不创建嵌套卡片或用颜色块替代信息结构。

备选方案是引入完整组件库或 Tailwind token；现有 renderer 规模和 CSP 不需要额外运行时或构建系统，迁移成本高于收益，因此拒绝。

### 3. 首页保留状态总览并按需切换聚焦列表

首页结构调整为：

```text
项目上下文 + 刷新状态
关键摘要（活跃 / 进行中 / 待归档 / 异常）
默认：状态分组（进行中 / 待归档 / 需要处理）
选择摘要后：状态筛选与对应提案列表
```

状态摘要负责在总览与聚焦列表间切换，状态分组负责默认扫描，提案卡片或提案行负责进入详情。默认执行台恢复原有状态列语义，固定顺序为进行中、待归档、需要处理；没有内容的分组只显示紧凑空状态，不渲染大块占位。点击具体摘要后使用紧凑表格完整展示该状态提案；选择活跃或全部则返回状态总览。宽窗口并列状态组，窄窗口改为横向滚动或单列堆叠，但名称、机器 ID、状态和进度始终可见。继续遵守首页不出现跨提案任务列表的既有产品边界。

以单一全量表格作为默认首页会使“执行台”退化为删除导航后的“提案运行”，丢失原执行台的状态总览语义，因此拒绝。紧凑表格仅用于用户主动选择状态后的聚焦查看。

### 4. 详情页采用任务主轴与可收敛上下文

详情页主轴固定为：身份与状态、精确进度、当前任务、任务阶段。当前任务使用紧凑焦点区并可定位到任务行，已完成任务降低视觉权重；文档、来源和警告位于次级上下文。

宽桌面以主栏加窄上下文栏展示；紧凑桌面将上下文放入同页次级区域；最小窗口使用可访问的折叠面板或标签保持其可达。文档页面采用受控阅读宽度和页面内目录，宽表格与代码块只在自身容器滚动。

备选方案是把 tasks 与 documents 做成完全互斥的顶层页面；这会切断执行时所需的上下文关联，因此保留相邻但不竞争的结构。

### 5. 使用离散断点而非连续压缩

布局按实际桌面任务定义三档：

- 宽桌面 `>= 1280px`：完整侧栏、任务主栏与上下文栏并列。
- 紧凑桌面 `960–1279px`：窄侧栏，上下文移至主内容下方或受控面板。
- 最小桌面 `820–959px`：图标化导航轨道与可打开的项目切换入口，单栏内容优先展示当前任务和提案。

固定格式控件使用明确 grid track、最小尺寸和溢出策略。字体不随 viewport width 缩放，页面级横向滚动视为失败；仅表格和代码等内容容器允许局部横向滚动。

### 6. 首轮动效只使用 CSS 与平台能力

状态切换、悬浮、展开和刷新使用短时 opacity、颜色和小幅位移动效，不做页面入场编排、磁吸按钮、滚动特效或循环装饰。所有动效必须可在 reduced motion 下退化为即时状态变化。

现有需求不需要 timeline、FLIP 或路径动画，加入 GSAP 会增加运行时和测试面。若后续引入可视化工作流并出现多元素编排需求，应通过独立 change 评估 GSAP，而不是在本 change 预装。

### 7. 用确定性 Electron fixture 建立质量门禁

核心和服务测试继续使用 `node:test`。UI 流程保留直接 Electron 自动化，并增加适合视觉断言的 Playwright Test 能力；fixture 固定标题、数量、时间、主题和字体环境，禁用非必要动画后生成基线。首批基线覆盖：

- 宽桌面浅色首页与提案详情。
- 紧凑桌面浅色提案详情。
- 820×640 浅色首页与详情。
- 宽桌面深色文档阅读。
- 项目管理的正常、失效和扫描候选状态。

视觉差异输出 baseline、actual、diff，由人工确认后显式更新。基线固定在 macOS/Electron 版本组合，避免跨平台字体差异造成噪声。可访问性使用小型开发依赖在首页、详情、文档和打开后的对话框分别执行；自动检查之外仍保留键盘、焦点、VoiceOver 名称和文本缩放人工清单。

Playwright MCP 擅长持续探索，但不提供本仓库可提交的确定性断言，因此只作为开发者本地可选工具。Storybook 会要求拆分独立组件运行环境和重复 mock，本项目页面数量不足以抵消其维护成本。

### 8. Skill 只影响设计与评审流程，不进入产品

Taste Skill 固定版本后用于原型审计，输出必须回写为本项目自己的设计决策，不能把外部 Skill 当隐式规范。Ponytail 只在实现完成后运行 review/lite 检查，重点阻止无必要框架、动画库、重复组件和架构漂移；不得以减少代码为由删除可访问性、视觉回归或安全处理。

### 9. 项目选择与提案入口使用单一交互路径

原生 `select` 的弹出层由操作系统绘制，暗色侧栏下的尺寸、颜色和选中态无法与应用控制，且项目名称较长时命中区域和反馈不稳定。项目切换改为应用内按钮与 listbox 菜单：整行按钮打开菜单，项目项同时展示名称、健康状态和当前标记，并支持方向键、Enter、Escape、焦点返回及点击外部关闭。项目管理继续由独立设置按钮承载，不塞入选择菜单。

“提案运行”与“执行台”读取同一批未归档提案，因此只移除“提案运行”独立主导航，仅保留执行台、规范和归档；这不授权删除或替换执行台原有的信息架构。`overview` 继续作为完整的执行台首页，保留项目上下文、刷新状态、四项摘要和按状态分组的提案总览，不能用原“提案运行”的全量集合表格替代。旧 `changes` 深链接继续兼容，但渲染时归一到默认状态总览；提案详情的返回入口也回到该首页。

执行台顶部四项摘要改为真实视图控件，顺序固定为活跃、进行中、待归档、需要处理；聚焦列表中的分段控件顺序固定为全部、进行中、待归档、需要处理。点击具体状态摘要在当前执行台打开对应提案列表，并同步列表标题和两个筛选区域的选中态；选择活跃或全部则显示原执行台的状态总览。状态聚焦属于执行台内的临时视图；用户显式点击“执行台”、切换项目或由旧 `changes` 路由进入时恢复状态总览。

### 10. APPICON 与内部产品标识使用独立资产

APPICON 使用用户指定的 1024×1024 方形金属徽章 JPEG，中央 `SPEC`、齿轮、线路和圆角底板共同构成 Finder 与 Dock 识别。输入 JPEG 无透明通道，底板外的棋盘格只是生成图中的假透明背景，不能作为最终 APPICON 像素保留。源 JPEG 保持不变，构建脚本按外层金属底板轮廓应用确定性的抗锯齿圆角 Alpha 蒙版，只移除底板外背景，保留中央白色 `SPEC`、金属高光与内部细节，再生成 RGBA Dock PNG 与 macOS ICNS。Electron Forge 使用 ICNS 打包，开发模式 Dock 使用 PNG。

应用内部产品标识使用用户指定的 512×512 透明 PNG，仅保留圆形金属徽章；完整侧栏和最小导航轨道直接消费该文件。内部标识不由 APPICON 派生，APPICON 也不再输出 renderer 副本。两张源图分别保存并由测试锁定哈希、尺寸、透明属性和消费路径，防止后续混用。

## Risks / Trade-offs

- [视觉重构改变大量截图，初次基线审阅成本较高] → 先固定 fixture 和页面矩阵，再分页面确认基线，禁止一次性无审阅更新全部截图。
- [Taste Skill v2 仍在演进，规则变化导致设计漂移] → 固定 commit，仅摘取适用原则，并以本 change 规格为最高约束。
- [单文件 renderer 在大规模结构调整后可读性下降] → 仅在重复和状态边界明确时拆分局部渲染 helper，不借视觉改造引入框架或通用组件层。
- [像素比较受字体和 Electron 版本影响] → 固定 macOS、Electron、主题、fixture 与动画设置，版本升级时单独审核基线。
- [自动可访问性检查无法覆盖全部体验] → 将自动规则作为下限，并保留键盘、焦点、VoiceOver 和文本放大人工验收。
- [高密度布局可能牺牲初次理解] → 两种密度原型都使用真实数据，在首次使用、日常扫描和最小窗口三个任务上比较后再选定。

## Migration Plan

1. 冻结当前关键截图与交互路径，建立确定性 fixture 和设计评审矩阵。
2. 产出均衡密度与高密度两套探索，完成宽、紧凑、最小窗口及明暗主题审阅，记录选定方向。
3. 先整理 token、排版、焦点和基础控件，再依次迁移应用框架、首页、详情、文档和项目管理，确保每一步均可回退。
4. 接入视觉基线、差异产物和自动可访问性检查，补齐键盘、文本溢出与 reduced motion 验收。
5. 在源代码 E2E 全绿后重新打包 macOS arm64/x64，并用打包版本复核关键页面。

回滚时保留新的 fixture 与测试基础设施，按页面恢复旧 renderer 结构和样式；不触碰 core、IPC 或项目注册数据，因此无需业务数据迁移。
