## Context

当前 `packagerConfig` 未声明覆盖策略，而 Electron Packager 在目标目录已存在时会跳过创建。`npm run package` 还按主机架构隐式选择输出；`out/` 被 Git 忽略，因此旧 `.app` 缺少可审计的版本边界。详见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 每次指定架构构建都产生可验证的新 `.app`，而不是复用历史目录。
- 让发布者能一眼看出构建了哪个架构，并能一条命令构建完整 macOS 集合。
- 在命令成功前验证包内受支持生产源码与工作区一致。

**Non-Goals:**

- 不引入代码签名、公证、自动更新、安装器格式或跨平台发布。
- 不把 `out/`、二进制应用包或发布元数据提交到 Git。
- 不要求整个仓库的每个文件都进入包内容指纹。

## Decisions

### 显式覆盖并按架构拆分命令

在 Forge 的 packager 配置中显式启用覆盖。保留 `arm64` 与 `x64` 专用命令，并将通用 macOS 发布命令定义为依次执行两个专用命令；命令链使用失败即停止的语义。

备选方案是每次在 shell 中手动删除 `out/`。该方式依赖人为操作、容易删除过宽范围，且不能阻止其他发布入口复用旧目录，因此不采用。

### 以包内生产源码摘要作为成功证据

新增独立 Node 验证脚本，接收明确架构并定位该架构的 `.app` 与 `app.asar`。它对受支持的生产入口集合计算摘要，并与从 `app.asar` 读出的同路径内容逐项比较；不一致、缺失或不可读均为失败。验证脚本需要直接声明其 ASAR 读取依赖，而不依赖 Forge 的传递依赖。

备选方案是只检查 `.app` 或 `app.asar` 的存在和修改时间。它们无法证明包内源码来自当前工作区，时间戳也可能被复制操作保留，因此不足以防止本次故障。

### 将验证置于每个架构打包命令之后

专用构建命令在 Forge 成功返回后立即调用验证脚本。完整 macOS 命令仅组合这些已经验证的专用命令，因此任何一个架构的打包或内容校验失败都会中止整体发布。

## Risks / Trade-offs

- [覆盖会删除目标架构的旧 `.app`] → 只让 Packager 操作明确的架构目录；失败后不会留下可被误认的新旧混合产物。
- [源文件集合遗漏关键生产文件] → 将集合集中定义、为验证脚本补充单元测试，并在新增生产入口时同步更新。
- [x64 构建增加本机发布耗时] → 提供独立架构命令；仅完整发布命令要求两个架构。
- [ASAR 工具的传递依赖变化] → 在开发依赖中显式声明 ASAR 读取库。

## Migration Plan

发布者改用明确的架构命令或完整 macOS 命令。若需要回滚，只需移除覆盖配置、验证脚本与新命令；`out/` 继续保持未跟踪状态。
