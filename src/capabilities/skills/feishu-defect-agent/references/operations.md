# 执行与恢复

在具体缺陷签名、交付、补证或恢复时阅读。命令入口为技能内 `scripts/defects.mjs`；通过 Node.js 调用，并使用绝对的绑定、状态与输入路径。

## 命令分工

| 命令 | 用途 |
| --- | --- |
| `doctor` | 诊断 CLI、个人身份、绑定和各独立通道 |
| `choices` | 只读列出当前飞书身份和项目绑定的近期配置候选 |
| `prepare` | 核对本次仓库/分支、群、APP、身份、交接与交付能力，保存短期准备回执 |
| `start` | 用已确认且仍有效的准备回执建立主运行；同一回执重用同一 run |
| `resume` | 恢复明确的原运行检查点，核对最新项目事实 |
| `stop` | 记录明确的停止原因，保留签名、待办和未知事务 |
| `suspend` | 失去处理权限后保存本地交接，保留外部签名 |
| `refresh` | 完整轻量扫描及必要证据复查，输出有界摘要 |
| `status` | 查看本地运行事实和下一批候选，不以此冒充远端刷新 |
| `detail` | 为选中的具体任务按需读取详情和证据 |
| `relations` | 按需读取真实关联到私有文件，由子任务判断依赖、重复及冲突 |
| `begin` | 核对当前负责人、状态和最新有效签名，开始持有处理签名 |
| `worker` | 准备具体排查任务及必要指针 |
| `worker-result` | 接收结构化子任务结果及证据位置 |
| `deliver` | 通过 `--phase` 调用 validate/commit/push/publish/verify，或 inherit/reconcile |
| `transition` | 无输入时保存实际流转选项；有输入时执行并回读状态 |
| `finish` | 确认已核验交付和状态回读后，写 done 结果签名 |
| `triage-result` | 仅排查模式：评论并私聊当前授权飞书账号，记录独立的排查结果 |
| `park` | 记录 wait_qa/handoff、补证等待状态、补证或交接及各通道结果 |
| `sync-qa-state` | 对已有 wait_qa 请求同步或回填 EVIDENCE_LACK 状态通道回执，不重发补证通知 |
| `handoff-result` | 核验已单独提交并推送的交接文档，同步共享提交引用 |
| `retry-notification` | 继续已知未发送的通知，或凭原运行持久意图恢复结果 |
| `update-notification` | 原位更新已确认 QA 卡片的创建者 @，保留原消息 ID |
| `reconcile` | 核对未知评论、状态流转及已有卡片更新，不重发不确定写入 |
| `host-link` | 保存已实际创建的宿主目标/任务 ID 映射 |
| `handover` | 在显式确认旧运行停止后记录可追踪接管 |

通用参数可选 `--binding FILE --state-dir DIR --identity-map FILE`。自动发现及个人状态位置见 [绑定与适配](binding.md#共享配置与个人身份)。已有运行加 `--run ID`，缺陷操作加 `--issue ID`。结构化数据用 `--input FILE`，命令帮助给出各操作的必填输入；不能用编造参数绕过缺失能力。`relations --input FILE` 接收已核对的官方 CLI 关联查询参数，只返回关联资料路径。

新 Target 按 [启动前向导](binding.md#启动前向导) 用 `choices` 展示本地候选，再将用户选定的 `reuse_run_id`、明确确认的 `mode` 和要修改的选项交给 `prepare`。`repair` 先完成 [发布管道确认](binding.md#发布管道确认)；`triage` 见 [仅排查](#仅排查)。只有本轮选择已确认、`ready: true` 且未超过 `expires_at` 才 `start`，输入为 `{"preparation_id":"本轮准备回执","confirmed":true}`。沿用选项会建立新 run；同一回执重试不另建 run。恢复原运行用 `resume`。

`candidate_limit` 只约束摘要输出。前一批被跳过、停放或处理后要继续补位，直到本地完整队列没有可执行项；不能把“摘要没有展开更多条目”当作空视图。

## 评论状态签名

机器记录由命令生成和解析，新写入格式为 `[Agent缺陷处理]v1.<base64url(canonical JSON)>`，读取兼容旧的标记后直接跟 JSON。编码段以 ASCII 传输机器 JSON，内容包含版本、项目/类型/缺陷键、actor、主 `run_id`、状态及记录时间；不要手写或编辑编码段。编码不代替评论作者核验，时间不触发自动过期。

1. 读取足以确认顺序与完整性的评论，核对作者、缺陷键和结构。仅正文偶然出现“处理中”无效；普通 QA 讨论不遮蔽 Agent 状态。
2. 选择最近有效状态记录。另一个主运行仍为 processing 时跳过；同一用户的不同 `run_id` 仍是其他运行。
3. 主 Agent 写自己的 processing 并回读核对结果，再派发排查。子 Agent 共用主运行归属，不自行写另一个签名。
4. 已完成、仅排查、wait_qa、handoff 或 cancelled 的结果使用同一归属记录终态，只能结束相匹配的 processing。已被接管的旧运行停止并保留本地资料，不能以旧终态覆盖新所有者。

无法确认评论完整性、作者或顺序时记录“签名未知”，不能假定无人处理。回读用于确认写入；本协议是协作避让，不提供原子互斥，也不增加锁、租约或极端同时进入的竞争机制。

中断的 processing 保留。接管必须明确确认旧运行已停止，再记录接管及新 processing；时间流逝、同一 actor 或缺少个人缓存均不构成接管依据。

## 主 Agent 的交付链

典型路径为：筛选可处理 → 签名 → 排查/补丁 → 验证 → 精确提交 → 推送 → 发布 → 核验 → 飞书结果及允许状态 → 结束签名。阶段表示执行事实，不替代工程计划或飞书业务状态。

主 Agent 审查子任务的实际差异与验证证据，再调用绑定的 `deliver --phase validate|commit|push|publish|verify`。提交仅含当前缺陷适用变更，遵循工程精确暂存和专属交付工具要求。Git push、CI 派发和原生 Task 勾选都不能替代发布核验。

`validate` 的输入文件明确主 Agent 已审查的实际变更路径，例如：

```json
{"reviewed": true, "changed_paths": ["src/changed-file.ts"]}
```

同仓库/通道上一条发布未核验前，不能开始下一条交付或把下一缺陷混入待发布内容。发布失败保留原提交、版本和结果；可继续不依赖该通道的工作，不能另升版本掩盖未知结果。

开始及重要动作前重新核对当前负责人、状态和有效签名；若转交他人或被其他运行接管，停止继续修改/交付并保存证据。原运行不再写能释放新所有者的终态签名。

先运行无输入的 `transition` 保存实际选项，只在需要时查看该选项文件。执行时提供真实 ID、目标状态和交付核验声明：

```json
{"transition_id": "实际允许的流转ID", "target_state": "实际目标状态键", "delivery_verified": true}
```

修复发布后按项目约定进入修复完成或待 QA 回归，不能直接宣称 QA 通过或关闭。缺少必填信息时只补确知的值，否则交接。成功回读后，以 `finish --input FILE` 提供 `{"reviewed": true, "summary": "实际结果摘要"}` 结束本条处理；不能仅因 delivery 对象存在就宣称核验完成。

重复缺陷被已核验交付覆盖时，用 `deliver --phase inherit --input FILE` 指定 `{"source_issue_key": "来源缺陷稳定键"}`，随后以 `{"reviewed": true, "changed_paths": []}` 独立执行 validate，再执行 verify 并记录来源缺陷、提交、发布及本条验证证据；不再创建 commit/push/publish。各自回写，不制造空提交或空版本。必要变更不可拆分且无法独立交付时先转裁决。

### 发布日志规范

主 Agent 在触发发布前写好本条缺陷的日志。用纯文本编号 `1.`、`2.`，一行一项，每项一句短话。首项写缺陷 ID 和用户可感知的修复；按需列已验证的结果、待 QA 回归的场景或影响验收的限制。省略实现过程、完整测试输出及机器人已展示的分支和提交信息。发布开始时只写本次变更和已执行的验证，不把待回归写成通过。

例如：

```text
1. 缺陷 7170625917：修复购买后 VIP 升级展示
2. 修复：同一笔购买只结算一次
3. 待回归：真实支付与结算
```

以所选 Jenkins Job 实际执行的脚本为准。若参数要求分隔符，从脚本核对完整字符序列、全角或半角及转义规则；只在条目之间按该规则传入。仅凭截图或口述无法确认时，先核对原始参数或脚本，不猜测符号。

已核对 WTC-Web `45ef5b6` 的 CV Debug：`message` 是多行参数，按条目直接换行。`ops/wtc-webapp-release/lib/release_notify.py` 会把 CRLF 和 CR 统一为 LF，不解析自定义分隔符。

该 WTC-Web 管道按 [飞书自定义机器人纯文本协议](https://open.feishu.cn/document/client-docs/bot-v3/add-custom-bot) 发送 `msg_type: text`、`content.text`，不依赖 Markdown 列表、表格、代码围栏或富文本。引号、反斜杠和换行交给 JSON 序列化处理；在 Jenkins 参数框不用手工转义，也不要输入字面量 `\n` 来换行。

## 外部动作与未知结果

每个动作分别保存 `intent → external_id/evidence → confirmed`；超时可能进入 `unknown`。恢复时先查已有提交、版本、运行 ID、评论、消息或实际状态，确认未发生后才按有限策略重试。

运行级 `reconcile` 回读评论、状态及已有卡片中的预期 @；交付阶段用 `deliver --phase reconcile --input FILE` 提供 `{"target_phase": "实际待核对阶段"}`，调用已配置的只读核对 hook。连续三次运行级核对后仍有未知副作用或未决交付阶段，运行进入 `fault`，原检查点继续保留。

没有幂等键或可检索关联证据时，如实标明无法自动判断。有限核对后交接或以待人工处理结束，不能声称端到端 exactly-once，也不能删掉检查点后重新派发。

发布能力或授权缺失时，记录已完成的源码阶段与剩余交付待办。状态回写只表达实际结果，不把“已改代码”写成完整修复闭环。

## 仅排查

`triage` 模式只读排查工程。主 Agent 核对实际证据，将简短结论整理为已确认的现象、证据和必要的下一步；不把推测写成已确认根因。将 `{"summary":"经核对的排查结论"}` 交给 `triage-result --input FILE`，摘要最多 4000 字节。

该命令在缺陷评论和私聊卡片上标注「仅为排查结论」，卡片带缺陷链接，只发给已核验的当前授权飞书账号。记录排查与通知结果后继续下一条；评论与通知各自核验，未知发送结果不盲重发。排查完成不改变缺陷业务状态，也不阻止后续直接修复。仅排查不改代码、不走仓库交接文档、`deliver` 或 `finish`。

缺少 QA 能提供的必要证据时，使用下方 `park` 的 `wait_qa` 流程，按工作流同步 `EVIDENCE_LACK`；确认不存在时保留原状态。不要先把未完成的补证请求当成排查结论发出。

## 补证与交接

信息不足时，`park` 先调用 `inspectEvidenceState` 只读检查该缺陷实际状态机、允许流转及必填项，保存状态计划。随后写入补证评论并完成可用 QA 通知，再同步可用的 `EVIDENCE_LACK` 并回读，使未知状态事务不会阻塞先前已授权的补证通知。已经处于该状态只核对，不重复写入。确认工作流不存在该状态时保持原 `OPEN` 或 `REOPEN`。状态存在但不可达、权限不足、查询失败或必填未完成都保留具体状态待办，不能冒充“不存在”或猜测流转 ID。

内部 `wait_qa` 签名与飞书业务状态分别记录。补证评论按下方规范编写；向本次 Target 已选 QA 群发送同一份清单及缺陷链接和优先级，使用缺陷 `create_by` 的已核验 IM 身份 @ 创建者。不能用负责人、报告人或同名成员替代；身份解析失败单独记录 `creator_mention: pending`，仍发送群卡片。状态、评论和卡片各自保存回执；已知未完成通道不妨碍其他独立补证步骤及后续缺陷。

`EVIDENCE_LACK` 同步不要求产品发布证据，也不记录修复完成；`triage` 仅允许这一补证等待状态例外。写入结果未知时只读核对实际状态，不能重发未知流转；未知事务仍按既有副作用规则处理。状态流转导致负责人变化时，保留已完成证据，不继续写覆盖新负责人或新运行签名的结果。

补证状态通道字段为 `qa_state`：`ready` 是可执行的只读计划，`pending` 表示缺少条件，`unknown` 表示状态写入结果待核对，`confirmed` 表示已核验状态或保持原状态的结论。确认没有 `EVIDENCE_LACK` 时记录 `status: "confirmed", supported: false`，不假造流转。实际写入使用独立的 `qa_transition` 事务，不能用来满足产品交付、修复状态同步或 `finish` 的前置条件。

已有共享 `wait_qa` 请求需要补齐状态同步或回填核对结果时，执行 `sync-qa-state --run ID --issue ID`，无需另建补证请求。若存在未知状态事务，先执行运行级 `reconcile` 只读核对，再执行 `sync-qa-state` 更新共享 `qa_state` 回执；不重发补证卡片或已经确认的状态流转。证据已变化时先审查新证据，不能沿用旧请求强制停回等待状态。

无法裁决或修复时用 `park --input FILE` 提供 `kind: "handoff"`、`summary` 和可选的 `questions`。写调查结论、阻塞、风险、补丁/证据和接续步骤，通知已映射的当前操作者。在 `handoff.directory` 指定的当前工程目录、本次已选分支生成可检索文档，返回 `pending_commit` 及相对路径，由主 Agent 审查并按工程规则在该分支单独提交该文档、推送，再用 `handoff-result --input FILE` 提供 `{"commit_oid": "实际完整提交OID"}`。命令核验该提交只包含此文档、blob 与当前内容一致、已包含于目标远端分支，再更新共享 handoff 文档回执为 confirmed。生成成功不等于提交完成，交接文档提交不触发产品发布。需要方案裁决时可建立工程适用的独立提案。

共享结果评论需保留请求标识、问题摘要、证据基线、补证状态同步结果、交接引用和已知通知结果。新运行据此恢复停放及未决步骤，不能因拿不到旧个人缓存就重复评论、状态流转或发送已确认卡片；未回填的结果按未知核对。

评论、卡片及文档各自记录成功、失败或未知。比如评论已核验而卡片失败，只处理未完成卡片，不再重复评论。通知去重包含缺陷、请求类型和证据版本，不每轮重发同一问题。

`retry-notification` 仅继续共享结果中已知未发送的 `pending` 通知；原运行还可凭自己的持久意图恢复未回填结果：已有 confirmed 结果直接复用，已知未发送记录或尚未派发的意图才可发送。其他运行看到 unknown 不能据此重发；当前证据与请求基线变化时，应先审查新证据。

已发送 QA 卡片需要补充创建者 @ 时，先按 [绑定与适配](binding.md) 核验身份或补齐个人映射，再对原运行/缺陷执行 `update-notification`。此命令只更新共享 wait_qa 结果中的 confirmed `feishu-app` 消息；证据仍须匹配原补证基线。它保存更新意图，以原 `message_id` PATCH 并 GET 回读，确认后同步共享回执；不重发卡片，未知更新结果也不能改成新发消息。身份未解析时保留原卡片及待办，继续其他独立工作。

卡片更新结果未知时，先 `refresh` 恢复共享更新意图，再 `reconcile` 按原消息核对真实 at 节点及其关联身份。确认后再次执行 `update-notification` 可复用已确认回执写回共享结果，不重复 PATCH 或发卡片。

更新回执中的 `alert: "not_guaranteed_for_message_update"` 必须保留。已有卡片加入 `<at>` 后，官方能力无法保证向被 @ 者新推送提醒；不能把消息更新成功报告为提醒已送达。新发卡片可直接包含已核验身份的真实 `<at>`。

### QA 补证评论规范

正文以「请补充」开头，接编号清单。每行一个 QA 能直接回答的字段或动作，只列缺失且会影响下一步排查的证据。能直接提供关卡 ID、版本号等值，就写明要哪个值；需要看具体画面时才索取截图。用短语或短句，不写「不需要提供」的清单、根因猜测或需要开发执行的调试步骤。

确实需要给 QA 解释原因或原理时，放在末尾「补充说明」单独一节；没有必要就省略。发送前确认 QA 即使不读说明，也能逐项回复。

新补证请求用 `park --input FILE` 提供 `kind: "wait_qa"` 和 `questions`（逐项填写，无需自带编号或「请补充」），仅在需要说明时提供 `summary`。例如，以下三项都缺失时：

```json
{"kind": "wait_qa", "questions": ["关卡 ID", "进入方式", "测试版本号"]}
```

```text
请补充：
1. 关卡 ID
2. 进入方式
3. 测试版本号
```

## 刷新、复活与终止

索引变化不代表全部证据变化。默认发现识别 `EVIDENCE_LACK`，已有 wait_qa/handoff 项每轮仍复查必要的描述、评论和附件，包括因此移出原视图的已关注补证项；只有证实覆盖范围的元数据才可缩小读取。所有已识别 Agent 的进度、签名、状态同步和重复提醒都不算 QA 新证据。证据未变继续 wait_qa；实质补证出现后重新评估状态、负责人及签名，满足实际工作流及可执行条件再入队，不能因 `OPEN/REOPEN` 筛选永久遗漏，也不自动改为 `FIXED`。

关注项移出视图也不能丢掉其未完成交付。保存来源关系及已关注事务，核对最新事实后决定继续或交接。

启动立即扫描，随后每 5 分钟复查。两次连续到期复查均为空时切换到每 30 分钟，发现可执行工作后恢复 5 分钟并清零。有效空轮要求分页和必要复查完整、身份可确认、无可执行或可继续处理项、无活跃子任务和未知事务。停放项可以计空。

读取失败不累计空轮，按有限预算处理；认证失败不自动重试。持续无法形成可靠轮次或核对未知结果时明确以故障/待人工处理结束。宿主休眠或暂停后重新取最新事实，不补写历史空轮。

明确停止循环时，先停止实际原生子任务，再用 `stop --input FILE` 提供 `{"reason": "实际停止原因", "workers_stopped": true}`；没有活跃子任务可省略后者。该命令保留签名、待办与未知事务。失去权限或被接管的任务，停止实际 worker 后用 `suspend` 提供 `{"worker_stopped": true, "reason": "实际原因"}`，只保存私有交接而保留外部签名；仍有权处理时应用 `park`。恢复用原 `run_id` 执行 `resume`，先核对未决事务，到期后再刷新。

退出摘要分别列出已交付或已排查、wait_qa、handoff、他人负责、其他运行处理中、失败及待人工事项。空闲时继续按到期时间刷新。当前运行结束后不创建守护或调度器继续唤醒。
